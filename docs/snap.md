# Snap — 支付后的意义确认器

> 独立开发 · Android · 进行中（阶段四 / 共六阶段）

## 一、产品定位

大多数记账工具解决的是"钱花去哪了"（事后对账），Snap 解决的是"这笔钱为什么花"（当场确认）。

支付完成后的几秒，是用户对这笔消费记忆最清晰的时刻。Snap 在这一刻弹出一个极轻的悬浮窗，让用户用一次点击完成"意义确认"：这笔钱属于什么、值不值得、下次还要不要。

一句话：**把每一笔支付，变成一次有意识的确认。**

## 二、目标用户与核心场景

| 用户 | 场景 | 痛点 |
| --- | --- | --- |
| 有记账习惯但坚持不下来的人 | 想记录但嫌麻烦，几天后就放弃 | 手动记账成本高 |
| 想控制冲动消费的学生 / 年轻上班族 | 月底发现钱莫名花光 | 消费时无感知 |
| 想复盘"钱花得值不值"的人 | 年底回看账单只有数字、没有情境 | 账单丢失了当时的决策语境 |

## 三、核心交互流程

1. 用户完成扫码 / 付款，停留在支付成功页；
2. Snap 通过 AccessibilityService 捕获支付完成事件与关键字段（金额、商户、时间）；
3. 悬浮窗在支付页上方弹出（不跳转、不阻断），提供：智能预选分类 → 一键确认 / 修改 / 补充备注；
4. 用户可选择"稍后处理"，交易进入待处理队列，不打断当下场景；
5. 数据写入本地 Room 数据库；
6. 摘要页与交易列表页提供回顾视图。

设计原则：**只打断一次、默认猜对、随时可跳过**。

## 四、技术架构

| 层 | 方案 |
| --- | --- |
| 事件采集 | AccessibilityService 监听窗口变化与页面文本，识别微信 / 支付宝等支付完成页 |
| 通知解析（规划） | NotificationListenerService 读取银行服务号推送，补全付款方式与资金来源 |
| 悬浮窗 | WindowManager + Jetpack Compose（独立窗口） |
| 数据层 | Room：交易表、分类表、待处理队列表 |
| UI | Compose：摘要页、交易列表、待处理队列、分类器 |

## 六、已知技术难点

1. **付款方式不可见**：微信支付成功页与输入页均不展示付款方式，只有预支付确认 BottomSheet 显示。需要在 BottomSheet 阶段截取，或从银行通知反推。
2. **资金来源提取**：尝试从微信银行服务号交易提示的后台通知数据中提取"零钱 / 某银行卡"信息。
3. **系统限制**：实机为荣耀 MagicOS（BRC-AN00），对后台存活、无障碍服务、悬浮窗权限有额外限制，需针对性适配。
4. **误触发控制**：仅在明确的支付完成页触发弹窗，避免在其他页面打扰。

## 七、设计取舍

- **本地优先**：交易数据存本地，不做云端同步（降低隐私风险与实现复杂度）。
- **低打扰**：一次弹窗、默认分类、可一键跳过。
- **分阶段验收**：每个阶段可运行、可回滚，不做"大爆炸式"开发。
